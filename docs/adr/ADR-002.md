# ADR-002: Database Migration — Knex.js + SQLite (Portable to PostgreSQL)

## Status
**Proposed**

## Context
The MVP stores all trip data in a single JSON file (`data/trips.json`) via `server/storageFile.js`. This approach was sufficient for the midterm prototype but has significant limitations documented in the midterm snapshot:

- Data does not persist across server restarts in some environments
- No support for concurrent users
- No deletion capability (no way to remove individual records)
- No relational integrity between trips and checklist items
- Cannot scale to a hosted deployment

The team is considering hosting the application on AWS for the beta release, which requires a real database. The storage layer must support both local development (lightweight, zero-config) and production deployment (managed database service like RDS PostgreSQL).

## Decision
We will migrate from JSON file storage to a **relational database** using **Knex.js** as the query builder, with **SQLite** for local development and a clear path to **PostgreSQL** for production.

### Why Knex.js
- **Database-agnostic query builder** — write queries once in JavaScript, Knex generates valid SQL for SQLite, PostgreSQL, MySQL, etc.
- **Built-in migration tooling** — schema changes are versioned and repeatable via `knex migrate:latest`
- **Built-in seed tooling** — replaces the custom `scripts/seed.js` with `knex seed:run`
- **Minimal abstraction** — not a full ORM, so the team still thinks in SQL and understands what runs
- **Swapping databases is a config change**, not a rewrite

### Normalized Schema

```sql
CREATE TABLE trips (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  destination_type TEXT NOT NULL,
  duration INTEGER NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE checklist_items (
  id TEXT NOT NULL,
  trip_id TEXT NOT NULL,
  name TEXT NOT NULL,
  category TEXT NOT NULL,
  packed BOOLEAN NOT NULL DEFAULT FALSE,
  sort_order INTEGER NOT NULL DEFAULT 0,
  FOREIGN KEY (trip_id) REFERENCES trips(id) ON DELETE CASCADE,
  PRIMARY KEY (trip_id, id)
);
```

**Why normalized instead of a JSON column:**
- Enables querying individual checklist items in the future (e.g., "show all unpacked items across trips")
- `ON DELETE CASCADE` gives us trip deletion for free — deleting a trip automatically removes its checklist items
- Schema is fully portable to PostgreSQL without modification
- Prepares for custom checklist items (add/remove/rename) planned for a later sprint

### Storage Interface

The new module (`server/storage.js`) will export the same functions as `storageFile.js` plus `deleteTrip`:

| Function | Behavior |
|----------|----------|
| `getAllTrips()` | Returns all trips with their checklist items |
| `getTripById(id)` | Returns one trip with checklist items, or `null` |
| `createTrip(params)` | Inserts trip + checklist items in a transaction, returns the created trip |
| `updateTrip(id, updates)` | Updates trip fields and replaces checklist items in a transaction |
| `deleteTrip(id)` | Deletes trip (cascade removes checklist items), throws if not found |

All multi-table writes will use **transactions** to prevent partial updates.

### Migration Path to PostgreSQL

1. Install `pg` package
2. Update `knexfile.js` production config to point at the PostgreSQL connection string
3. Run `knex migrate:latest` against the production database
4. No application code changes required

## Implementation Steps

1. **Install dependencies:** `npm install knex better-sqlite3`
2. **Create `knexfile.js`** — configuration for development (SQLite) and production (PostgreSQL) environments
3. **Create Knex migration** — `migrations/001_create_trips_and_checklist_items.js` defining both tables
4. **Create Knex seed** — `seeds/demo_trips.js` replacing `scripts/seed.js` with the same 3 demo trips
5. **Create `server/storage.js`** — new storage module using Knex, exporting the same interface
6. **Update `server.js`** — change import from `./server/storageFile.js` to `./server/storage.js`, add `deleteTrip`
7. **Add `DELETE /api/trips/:tripId` route** — returns `204` on success, `404` if not found
8. **Add `deleteTrip` to frontend API client** — add to `src/apiClient.js` and export `deleteTripOnServer` from `src/storage.js` to match existing pattern (`saveTripToServer`, `updateTripOnServer`)
9. **Update tests** — swap `beforeEach` from deleting JSON file to rolling back/re-migrating the test database; rewrite boundary test (currently imports `storageFile.js` directly) to use new storage module
10. **Update `package.json` scripts** — add `db:migrate`, `db:seed`, and `db:reset` commands; point `npm run seed` at `knex seed:run`
11. **Update OpenAPI spec** — document the new `DELETE` endpoint
12. **Verify `.gitignore`** — `data/` is already ignored, which covers `data/*.db`; no change needed

### Out of scope for this PR

- **Delete button UI in `src/main.js`** — ships with issue #49 (Trip deletion) to keep this PR focused on the storage migration

### Notes

- **Naming:** `src/storage.js` is the existing frontend API client (wraps `src/apiClient.js`). The new backend module at `server/storage.js` lives in a different directory — no conflict, but the team should be aware of the distinction.
- **CI:** The pipeline runs on `ubuntu-latest`, which has native build tools pre-installed. `better-sqlite3` should compile without issues, but the first PR CI run will confirm this.
- **`scripts/seed.js`:** Will be superseded by the Knex seed file. The old script can remain temporarily for reference but `npm run seed` should point to `knex seed:run`.

## Consequences

**Positive:**
- Trip data persists reliably across server restarts
- Deletion is supported with referential integrity
- Same codebase runs locally (SQLite) and in production (PostgreSQL)
- Schema migrations are versioned and repeatable
- Transactions prevent data corruption from partial writes

**Negative:**
- `better-sqlite3` requires a native build step (node-gyp) — if this fails on a team member's machine, `sql.js` (pure WebAssembly) is a fallback
- Slightly more complex local setup (`knex migrate:latest` before first run)
- Two-table reads require a JOIN or two queries per trip (minor performance cost at this scale)

## Revisit Trigger
This decision should be revisited when:
- The team selects a specific AWS service (RDS, Aurora, etc.) and needs to finalize the production config
- The data model grows beyond trips and checklist items (e.g., user accounts, shared trips)
