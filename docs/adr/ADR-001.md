
# ADR-001: Authentication & Identity

## Status
**Accepted** (Amended: March 22, 2026)

## Context
The "Smart Packing Checklist Generator" is a web application designed for travelers to generate and customize trip-specific packing lists. 

**Initial Context (Prototype Phase):** The application was intended as a single-user prototype with no authentication. However, as the project evolved beyond a simple prototype, the need for multi-user support and data isolation became apparent.

**Current Context (Beta Phase):** The application now requires:
- User-specific trip management (each user sees only their trips)
- Data persistence and isolation across multiple users
- Secure authentication without managing passwords

## Decision
We will implement **Google OAuth 2.0 authentication** for user identity and data isolation.

### Authentication Strategy
- Users authenticate via Google OAuth 2.0, leveraging Google's secure authentication infrastructure
- No passwords are stored; authentication is delegated to Google
- Each user has an isolated view of their trips and checklists
- Sessions are managed using `express-session` with secure cookies

### Technology Stack
- **Passport.js** with `passport-google-oauth20` strategy for OAuth flow
- **SQLite** database with users table for user profile storage
- Foreign key relationship between users and trips for data isolation
- Session middleware (`express-session`) for maintaining authentication state

### Data Model
- **Users Table**: Stores Google profile (ID, email, name, picture)
- **Trips Table**: Modified to include `user_id` foreign key for ownership
- **Checklist Items Table**: Cascades with trips, ensuring data isolation

## Consequences

**Positive:**
- **Low Overhead Authentication**: OAuth eliminates the need to manage passwords, recovery flows, or account verification
- **User Data Isolation**: Each user's trips are isolated via user_id foreign keys; users can only access their own data
- **Scalability**: OAuth provider (Google) handles authentication load and security best practices
- **User Trust**: Leverages users' existing Google accounts; no need to create new credentials
- **Multi-Device Access**: Users can access their trips from any device by logging in with Google

**Negative:**
- **External Dependency**: Authentication relies on Google's services; if Google is unavailable, users cannot log in
- **Data Sharing Limitations**: The current model doesn't support sharing trips between users (future enhancement)
- **OAuth Configuration Required**: Developers must set up Google OAuth credentials in Google Cloud Console

## Implementation Details
- Google OAuth callback redirects to `http://localhost:5173/auth/google/callback` (or production URL)
- Authenticated endpoints require middleware check: `requireAuth(req, res, next)`
- User context is available via `req.user` after authentication
- Database migrations consolidated into single file for schema management

## Revisit Trigger
This decision should be revisited if:
- Trip sharing/collaboration features are implemented (may require role-based access control)
- Different authentication providers become necessary
- Authentication performance becomes a bottleneck
