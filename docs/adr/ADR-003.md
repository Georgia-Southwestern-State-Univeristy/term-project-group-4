# ADR-003: Beta Hosting on Elastic Beanstalk with SQLite on Attached EBS

## Status
**Accepted** (March 28, 2026)

## Context
ADR-002 proposed a database path that stayed portable to PostgreSQL, but the Week 11 beta deadline required a hosted environment with lower operational overhead than introducing RDS immediately.

The application already runs on SQLite (`better-sqlite3`) in development and test. For beta hosting, the team needed:

- Persistent storage across instance restarts/replacements
- Low setup complexity for a small team
- A production deployment path in GitHub Actions

## Decision
For beta, we host a **single-instance AWS Elastic Beanstalk Node.js environment** and keep the application database as **SQLite stored on an attached EBS volume** mounted at `/data`.

Implementation details chosen with this decision:

- Production Knex uses `better-sqlite3` with `SQLITE_PATH`.
- Environment variable target is `SQLITE_PATH=/data/trips.db`.
- EC2 instance remains single-instance (no horizontal scaling for beta).
- EBS mount and migration behavior are automated in deployment hooks.
- CI/CD deploys from GitHub Actions to EB using OIDC-based IAM role assumption.

## Implemented Evidence
As of March 28, 2026, the decision is implemented on branch `week11/aws-beta-hosting`:

- `knexfile.js`: production driver changed from PostgreSQL to SQLite (`better-sqlite3`)
- `server.js`: production storage readiness checks, `/health`, production static serving, and hardened session/proxy settings
- `server/logger.js`: production logging to stdout/stderr (EB-friendly)
- `.github/workflows/deploy-eb.yaml`: CI/CD pipeline for Elastic Beanstalk deploy
- `Procfile`: EB process entrypoint
- `.ebextensions/00_environment.config`: EB environment defaults
- `.platform/confighooks/predeploy/01_mount_ebs.sh`: attach/mount EBS volume
- `.platform/hooks/predeploy/02_migrate.sh`: run Knex migrations during deploy

Infrastructure created for beta deployment:

- EB application: `smart-packing-checklist`
- EB environment: `spcg-prod`
- Artifact S3 bucket for deploy bundles
- IAM service role, instance profile, and GitHub Actions OIDC deploy role
- Attached EBS volume for SQLite persistence

## Alternatives Considered

### 1. Elastic Beanstalk + RDS PostgreSQL

Pros:
- Better long-term scaling and availability options
- Clearer path to multi-instance deployment

Cons:
- More infrastructure to provision and secure now
- Additional migration/ops overhead during a short beta timeline

Decision: Deferred until post-beta re-evaluation.

### 2. SQLite on ephemeral instance storage

Pros:
- Fastest initial deployment

Cons:
- Data loss risk on replacement/redeploy
- Does not meet persistence requirements

Decision: Rejected.

### 3. ECS/Fargate container deployment

Pros:
- Flexible deployment architecture

Cons:
- Added complexity not justified for current scope/timeline

Decision: Rejected for beta.

## Consequences

**Positive:**

- Fastest path from local architecture to hosted beta
- Lower operational burden than introducing a separate managed database now
- Preserves data persistence when EBS mount hook succeeds

**Negative:**

- Single-instance design (limited availability and scale)
- Persistence tied to EBS lifecycle and mount correctness
- More operational sensitivity than fully managed database services

## Risks and Mitigations

1. Risk: EBS is not mounted before app writes begin.
- Mitigation: predeploy mount hook and production startup path checks.

2. Risk: Instance replacement does not reattach/remount as expected.
- Mitigation: automated attach/mount script and post-deploy verification checks.

3. Risk: Secrets/env config drift causes deploy/runtime failures.
- Mitigation: GitHub Actions secrets + EB environment property checklist and health endpoint validation.

## Revisit Trigger
Revisit this decision after beta if any of the following become true:

- Multi-instance scaling or high availability is required
- Backup/restore and durability requirements exceed single-volume operations
- Operational overhead of EBS attach/mount management becomes a recurring issue

At that point, migrate production hosting to RDS/PostgreSQL while keeping Knex migrations as the migration path.
